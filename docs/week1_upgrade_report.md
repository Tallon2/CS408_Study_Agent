## 1. 升级目标与背景

### 1.1 背景

408学习Agent 原始版本（v1.0）采用单一向量检索方案：用户问题经 Embedding 模型编码后，直接在向量数据库中做余弦相似度检索，召回 Top-K 文档块送入 LLM 作答。该方案在语义理解上表现尚可，但存在以下明显短板：

- **精确词汇命中弱**：向量检索对专有名词（如"进程控制块PCB"、"B+树"）的精确匹配能力不如关键词检索；
- **单块语义割裂**：固定长度分块导致跨块知识被截断，检索到"半段话"；
- **无质量过滤**：低相关度文档直接进入 LLM 上下文，产生噪声干扰；
- **单次检索无兜底**：检索质量差时没有重写-重检机制；
- **无可解释性**：文档来源单一，无法追踪检索路径。

### 1.2 升级目标

| 目标维度 | 具体指标 |
|----------|----------|
| 召回质量 | Hit@5 从 0.80 提升至 ≥ 0.90 |
| 排序质量 | MRR 从 0.64 提升至 ≥ 0.75 |
| 系统健壮性 | Reranker API 故障时自动降级，不中断服务 |
| 可维护性 | 模块化拆分，每个组件单独可测试 |
| 面试竞争力 | 覆盖混合检索、RRF、Reranker、Auto-merging 等企业级技术点 |

### 1.3 技术选型概述

```
向量检索（语义）  +  BM25（关键词）  →  RRF融合  →  评分门控  →  Reranker精排
```

这是目前工业界（Elasticsearch + Dense Retrieval）主流的混合检索范式，在 RAG 系统评测中普遍比纯向量检索高出 10–30%。

## 3. 核心技术改造详情

### 3.1 混合检索：向量检索 + BM25 稀疏检索

#### 技术原理

两种检索方式互补：

| 维度 | 向量检索（Dense） | BM25 稀疏检索 |
|------|-------------------|---------------|
| 核心思想 | 语义空间距离 | 词频-逆文档频率统计 |
| 优势 | 同义词、跨语言语义理解 | 精确关键词、专有名词命中 |
| 劣势 | 专有名词模糊、"幻觉相似" | 无法理解同义词和上下文 |
| 典型场景 | "内存管理相关内容" | "PCB进程控制块数据结构" |

#### 实现细节（`memory/rag/bm25_retriever.py`）

- **分词器**：jieba 中文分词，支持自定义专业词库（OS/网络术语）
- **索引持久化**：序列化为 JSON 格式，支持增量更新，无需每次重建
- **一键构建**：`scripts/build_bm25_index.py` 扫描全量文档自动建索引

#### 代码示例

```python
# BM25 检索调用示例
from memory.rag.bm25_retriever import BM25Retriever

retriever = BM25Retriever.load("bm25_index.json")
results = retriever.search("进程控制块PCB", top_k=5)
# 返回: [{"doc_id": "...", "score": 2.34, "text": "..."}]
```

### 3.2 RRF 融合算法

#### 数学公式

$$\text{RRF\_score}(d) = \sum_{r \in \text{rankers}} \frac{1}{k + \text{rank}_r(d)}$$

其中：
- $d$ 为候选文档
- $\text{rank}_r(d)$ 为文档 $d$ 在检索器 $r$ 中的排名（从1开始）
- $k = 60$（平滑常数，防止头部文档分数过高）

**实现代码（`memory/rag/hybrid_fusion.py`）：**

```python
def rrf_fusion(vector_results, bm25_results, k=60):
    scores = {}
    sources = {}

    for rank, doc in enumerate(vector_results, start=1):
        doc_id = doc["doc_id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
        sources.setdefault(doc_id, set()).add("in_vector")

    for rank, doc in enumerate(bm25_results, start=1):
        doc_id = doc["doc_id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
        sources.setdefault(doc_id, set()).add("in_bm25")

    # 按融合分降序，双路命中文档自然排前
    return sorted(scores.items(), key=lambda x: -x[1])
```

#### 参数选择理由

**为什么 k=60？**  
k 是平滑常数，防止排名第1的文档因 `1/(60+1)≈0.016` 独占优势。实验表明 k=60 在多路融合中能平衡"头部压制"与"尾部抑制"，是学术界和工业界的默认最优值（Cormack et al., 2009）。

#### in_vector / in_bm25 来源标记的作用

- **可解释性**：每条检索结果携带来源标记，便于 Debug 和日志分析
- **质量评估**：双路同时命中（`in_vector ∩ in_bm25`）的文档可靠性最高
- **测试验证**：5条输入去重后保留5条，最高RRF分 0.0325，双路命中标记经过自动化验证

### 3.3 评分门控 + Query 重写二次检索

#### 三档阈值设计（`memory/rag/score_gate.py`）

```python
GATE_THRESHOLDS = {
    "strict": 0.03,   # 严格模式：考试题精确查找，要求高置信度
    "normal": 0.02,   # 普通模式：日常问答，均衡精召率
    "loose":  0.01,   # 宽松模式：发散性探索，允许较低相关度
}
```

| 模式 | 适用场景 | 行为描述 |
|------|----------|----------|
| `strict` | 精确题目检索、定义查找 | 阈值0.03，严格过滤，宁缺毋滥 |
| `normal` | 大多数问答场景（默认） | 阈值0.02，平衡精召 |
| `loose`  | 探索性提问、开放问答 | 阈值0.01，召回优先 |

#### 门控未通过的兜底策略

```
融合候选列表
     │
     ▼ 最高分 < 对应阈值?
   ┌─Yes──────────────────────────────────────┐
   │                                          │
   ▼                                          │
QueryRewriter 重写查询                         │
   │ (decompose 子问题分解 或 expand 扩展)     │
   ▼                                          │
重新双路检索                                   │
   │                                          │
   ▼ 仍未达阈值?                              │
   └──── Top-3 强制兜底（至少返回3条）←────────┘
         保证 LLM 不空手作答
```

**Top-3 兜底逻辑**：无论门控是否通过，系统始终返回至少3条得分最高的文档，避免 LLM 因上下文为空产生幻觉。

### 3.4 三级滑动窗口分块 + Auto-merging

#### 三级参数（`memory/rag/indexer.py`）

```python
# 三级层次化分块配置
CHUNK_CONFIG = {
    "L1": {"size": 1200, "overlap": 200},  # 大块：完整小节级别
    "L2": {"size":  600, "overlap": 100},  # 中块：段落级别（默认检索单元）
    "L3": {"size":  200, "overlap":  50},  # 小块：句子/定义级别
}
```

**验证数据**：2700字文档 → L1×2 / L2×5 / L3×18，parent_index 分布正确。

#### 层级关系示意

```
原始文档 (2700字)
├── L1_chunk_0 (1200字)  ← 大段落，Auto-merge目标
│   ├── L2_chunk_0 (600字)
│   │   ├── L3_chunk_0 (200字)
│   │   ├── L3_chunk_1 (200字)
│   │   └── L3_chunk_2 (200字)
│   └── L2_chunk_1 (600字)
│       └── ...
└── L1_chunk_1 (1200字)
    └── ...
```

#### Auto-merging 原理

**经典问题：语义割裂**

> 例：检索"操作系统内存分页机制"，向量检索命中了 L3_chunk_5（仅包含"页表项格式"），但完整答案分布在 L2_chunk_2 的整段文字中。直接用 L3 文本送给 LLM，上下文不完整，答案残缺。

**Auto-merging 解法**：

```python
def auto_merge_context(retrieved_chunks):
    """
    当同一父块下有 ≥2 个子块被检索到时，
    自动用父块（L2/L1）的完整文本替换所有子块。
    """
    parent_hits = count_parent_hits(retrieved_chunks)
    merged_results = []
    for chunk in retrieved_chunks:
        if parent_hits[chunk.parent_id] >= 2:
            # 替换为父块完整文本
            merged_results.append(get_parent_chunk(chunk.parent_id))
        else:
            merged_results.append(chunk)
    return deduplicate(merged_results)

# 验证结果: merged=True，成功用父块文本替换子块
```

**效果**：解决了"检索片段句子、LLM 缺乏完整语境"的根本问题，同时不增加噪声块数量（替换而非追加）。

### 3.5 QueryRewriter 模块（三种策略）

#### 模块说明（`memory/rag/query_rewriter.py`）

```python
class QueryRewriter:
    """
    三种查询重写策略，应对不同场景的检索失效问题。
    """
    def expand(self, query: str) -> list[str]:
        """同义词/相关词扩展，解决词汇差距问题"""

    def decompose(self, query: str) -> list[str]:
        """复杂问题拆分为多个子问题，解决多跳检索问题"""

    def hyde(self, query: str) -> str:
        """HyDE: 生成假设答案文档，用答案的向量检索文档"""
```

#### 三种策略适用场景

| 策略 | 全称 | 适用场景 | 示例 |
|------|------|----------|------|
| `expand` | 查询扩展 | 专有名词有多种表述，单一词汇召回不全 | "内存管理" → ["内存管理", "存储管理", "虚拟内存", "页式管理"] |
| `decompose` | 子问题分解 | 复合问题跨越多个知识点，单次检索覆盖不全 | "比较进程和线程的区别及各自的调度算法" → ["进程vs线程区别", "进程调度算法", "线程调度算法"] |
| `HyDE` | 假设文档嵌入 | 问题与文档表述风格差异大，语义空间偏移 | 先让LLM生成一段假设答案，再用该答案的Embedding检索真实文档 |

#### HyDE 工作原理

```
用户问题: "什么是写时复制(COW)?"
     │
     ▼  LLM 生成假设答案
"写时复制是一种内存优化技术，当多个进程共享同一内存页时..."
     │
     ▼  对假设答案做 Embedding
[0.12, -0.34, 0.87, ...]   ← 假设答案向量
     │
     ▼  用假设答案向量检索真实文档
→ 命中"操作系统内存管理第3章-页面共享机制"（高度匹配）
```

**核心洞察**：文档-文档 的语义距离通常比 问题-文档 的语义距离更小，HyDE 通过"语义桥接"提升跨领域检索准确率。

### 3.6 专业 Reranker（API + LLM 双层降级）

#### 三层降级链设计

```
检索候选文档列表
        │
        ▼
┌───────────────────┐
│  Layer 1          │  首选：Jina Reranker API
│  Jina Reranker    │  · 专业交叉编码器精排
│  API 调用         │  · 基于 query-doc 对打分
└───────┬───────────┘
        │ API 失败/超时 (httpx 异常捕获)
        ▼
┌───────────────────┐
│  Layer 2          │  降级1：LLM Rerank
│  LLM 重排序       │  · 调用本地/远程 LLM
│  (本地/远程)      │  · Prompt引导排序判断
└───────┬───────────┘
        │ LLM 也不可用
        ▼
┌───────────────────┐
│  Layer 3          │  降级2：直通
│  RRF 原序直通     │  · 直接使用 RRF 融合顺序
│  (无额外计算)     │  · 保证服务永不中断
└───────────────────┘
```

**降级链价值**：
- **Jina API** 提供最高精排质量（Cross-Encoder，理解查询-文档交互）
- **LLM Rerank** 作为软降级，质量次之但仍优于 Bi-Encoder 排序
- **RRF原序** 作为最终兜底，确保任何情况下系统均可正常返回结果

**依赖**：新增 `httpx`（异步HTTP请求）、`numpy`（分数计算）到 `requirements.txt`。

## 6. 面试问答参考

### Q1：BM25 和向量检索各有什么优缺点？

**参考回答要点：**

> **向量检索（Dense Retrieval）**：
> - 优点：理解语义，能处理同义词、近义表述、跨语言场景；适合"描述性"问题
> - 缺点：对专有名词（如"PCB"、"CSMA/CD"）精确匹配弱；向量空间可能存在"虚假相似"；需要 GPU 加速，索引占用大
>
> **BM25（稀疏检索）**：
> - 优点：关键词精确命中，对专有名词、型号、代码等极为有效；无需 GPU，索引小，可解释性强
> - 缺点：纯词频统计，无法理解同义词（"内存"和"存储器"视为完全不同）；不能处理跨语言
>
> **最佳实践**：二者互补，RRF 融合是工业界标配，兼顾语义理解和精确匹配。

---

### Q2：为什么用 RRF 而不是直接加权平均？

**参考回答要点：**

> **加权平均的问题**：向量检索返回的是余弦相似度（0~1），BM25 返回的是 TF-IDF 分数（无上界，可达几十），两者量纲完全不同，直接加权需要额外归一化，归一化方式的选择本身引入超参，且对极端分布敏感。
>
> **RRF 的优势**：
> 1. **只用排名，不用原始分数**，天然解决量纲不一致问题
> 2. **k=60 平滑常数**防止头部文档垄断，保留长尾候选的价值
> 3. **无需调参**（除 k 值外），实现简单，效果稳定
> 4. **理论保证**：Cormack et al. 2009 证明 RRF 在多路融合中接近最优

---

### Q3：评分门控的阈值怎么确定？

**参考回答要点：**

> **经验 + 数据驱动**的两步法：
>
> **Step 1 - 经验初值**：根据向量检索余弦相似度的经验分布，通常 >0.7 为高相关，但经过 RRF 归一化后分数域变化。初始值参考 RRF 最高分的分布（如所有测试查询的 P10/P50/P90 分位）。
>
> **Step 2 - 标注集调优**：在 evaluation/test_cases.json 的 30 条标注数据上，枚举阈值 [0.005, 0.01, 0.015, 0.02, 0.025, 0.03]，选择 F1@3 最高的值。
>
> **三档设计理由**：不同业务场景对精确率/召回率的权衡不同——考试精确题目需要 strict，日常答疑用 normal 即可，探索学习用 loose 保证覆盖面。

### Q4：Auto-merging 解决了什么问题？

**参考回答要点：**

> **问题根源**：RAG 系统为提升检索精度，通常使用小粒度分块（如 200字的 L3 块），但 LLM 生成答案需要完整的上下文段落。
>
> **两难困境**：
> - 分块太大 → 向量检索准确率下降（块内噪声多）
> - 分块太小 → 检索到的文本语义残缺，LLM 无法完整作答
>
> **Auto-merging 的解法**：
> 1. **索引阶段**：同时建立多级分块索引（L1大/L2中/L3小），并记录 parent_index
> 2. **检索阶段**：用小块（L3）做精准检索，命中率高
> 3. **合并阶段**：若同一父块下有 ≥2 个子块被命中，用父块完整文本替换所有子块
> 4. **效果**：既保证了检索精准性，又保证了 LLM 获得完整语境
>
> **类比**：好比图书馆查书，用关键词找到了某本书的某一页（精准），但给你看的是整章内容（完整）。

---

### Q5：如果 Reranker API 挂了怎么办？

**参考回答要点：**

> **设计原则**：服务降级（Graceful Degradation），而非直接报错。
>
> **三层降级链实现**：
> ```
> try:
>     results = jina_reranker_api(query, docs)   # 最优质量
> except (httpx.TimeoutException, httpx.HTTPError):
>     try:
>         results = llm_rerank(query, docs)       # 次优质量
>     except Exception:
>         results = rrf_ordered_docs              # 最终兜底，不中断服务
> ```
>
> **关键设计点**：
> 1. **超时控制**：对 Jina API 设置 3~5秒超时，避免阻塞整个管线
> 2. **异步调用**：使用 httpx 异步 HTTP，不阻塞主线程
> 3. **兜底保证**：RRF 原序本身已经是较好的排序，降级后质量损失有限
> 4. **监控告警**：记录降级日志，便于发现 API 故障并及时修复
>
> **面试加分**：提到"熔断器模式"（Circuit Breaker），当 API 连续失败 N 次后自动切换到降级路径，避免每次都等待超时。
